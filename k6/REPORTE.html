Sistema de Tickets — Helpdesk Empresarial 23 de septiembre de 2026 Grafana k6 · PostgreSQL 16 · Node.js 22

1. Resumen ejecutivo

Se sometió el sistema a dos escenarios de carga concurrente: uno de capacidad pura de escritura y otro con una proporción de uso realista. En conjunto se enviaron 6.421 peticiones y se crearon 3.615 tickets sin un solo error de servidor.

Conclusión: el sistema es estable bajo carga. El primer cuello de botella está identificado —el pool de conexiones a PostgreSQL— y es configurable sin tocar código.

2. Método

  1. Levantar el sistema con Docker Compose y cargar el semillero de demostración.
  2. Desactivar los tres limitadores de tasa: sin este paso la prueba mide el limitador, no el sistema.
  3. Ejecutar la prueba de humo (10 pasos funcionales) y solo continuar si pasa.
  4. Ejecutar los escenarios y comparar contra umbrales definidos de antemano.

k6 devuelve código de salida distinto de cero si un umbral se incumple, así que el resultado no es una interpretación: es una verificación.

6. Diagnóstico

Con DB_POOL_MAX=10 el p(95) del escenario tasa sube a ~5.200 ms; con DB_POOL_MAX=50 baja a 1.478,95 ms. El código no cambió: cambió cuántas consultas puede tener en vuelo la aplicación.

El p(99) de 12,4 s frente a un p(95) de 1,5 s es la firma de un pool saturado: la mayoría pasa rápido y una minoría espera una conexión libre.

El script autentica una sola vez por usuario virtual y reutiliza el token. Es deliberado: bcrypt con coste 12 tarda unos 100 ms por verificación y, si se autenticara en cada iteración, la prueba mediría el costo del hash y no el del endpoint de tickets.

7. Limitaciones

  • Una sola instancia: no se probó escalado horizontal.
  • Entorno de desarrollo: los valores absolutos no son trasladables, pero la forma de la curva y el cuello de botella sí.
  • El frontend no participa: se mide la API, que es donde está el costo.
  • No se probó con volúmenes de producción.
Las 13 comprobaciones no superadas del escenario tasa (0,06 % de 20.814) son verificaciones de latencia individual durante la cola máxima. No hubo ningún error 5xx ni ningún 429, y todos los umbrales agregados se cumplieron.
